# 实验一需求分析与 OpenCV 环境基线报告

本实验建立图像读取、属性检查、灰度转换和保存的最小链路，并交付需求规格、独立环境、命令行代码、测试工具和运行证据。基线代码已完成 21 项程序自检，并用用户提供的图片及其派生版本完成 17 项正式测试，全部通过。

## 实验背景与目标

视觉程序交付不仅要求算法能够计算，还要求输入输出、像素类型、通道顺序和失败反馈一致。此次目标是让自行提供的动漫或图形素材拥有稳定入口，明确原图保护和可验证的验收条件。实现范围止于实验一，不执行后续实验的处理算法。

## 需求分析结果

`requirements.md` 给出 8 条功能需求、5 条非功能需求、6 条异常处理需求、4 个用户用例及 9 条验收标准，每项均关联验证方式。核心约定为：输入路径参数化；读取后检查 shape/dtype/ndim/channels；灰度保持像素，彩色按 BGR 转灰度，四通道舍弃 Alpha；尺寸与位深保持；输出为无损单通道 PNG。

## 环境与目录

本次 Windows 11 AMD64 环境使用 Python 3.14.7、OpenCV 5.0.0、NumPy 2.5.4、Matplotlib 3.11.2。所有依赖安装在 `project_i/.venv`，实际安装包版本锁定在 `requirements.txt`。操作系统完整信息和解释器路径由 `version_check.py` 采集，见 `environment.md`。

项目按指导书设置 `src`、`data/input`、`data/output`、`docs`、`evidence`，另增加 `config/images.json` 存放可替换路径。原始输入、灰度结果和证据分离。按最新要求，实验一个人结果及证据固定为 lab1_latest；新结果通过校验后替换旧结果。

## 基线程序设计与关键代码

`baseline_pipeline.py` 通过 argparse 接收 `--input`、`--output` 及可选的 `--record`。程序从路径读取字节，调用 `cv2.imdecode(..., IMREAD_UNCHANGED)` 解码。与直接传文件名给图像接口相比，这个路径可由 Python 正确处理中文文件名；仍使用 OpenCV 完成图像解码。

解码返回空对象时立即报错，不访问 shape。随后 `validate_image` 限定二维灰度或三/四通道数组，像素类型只接受 uint8 和 uint16。`to_gray` 对二维数组直接返回，对彩色使用 `cv2.cvtColor(image[:, :, :3], cv2.COLOR_BGR2GRAY)`，从而遵循指导书的 Alpha 舍弃策略。

输出先进行 PNG 编码，写入同目录临时文件后原子替换目标，以降低保存中断造成半写入文件的风险。再次回读输出验证形状、位深和每个像素。`common.py` 禁止写入 `data/input`，拒绝输入输出相同及冲突的日志路径。正常与异常都通过可解析状态和退出码反馈。

输入是 NumPy 像素数组：`img[y,x]` 表示行列位置；彩色采用 BGR/BGRA，灰度为单通道。转换没有调整空间分辨率；16 位数据没有缩为 8 位，也没有拉伸对比度。

2026 年 10 月 13 日，本机执行 21 项程序自检，21 项通过，非预期失败为 0，所有输入前后 SHA-256 相同。覆盖彩色 PNG、JPEG、灰度、Alpha、中文路径、损坏文件、新建输出目录、黑白图、不同尺寸、大图、保存路径保护、16 位输入，以及非法类型和通道的拒绝。

已知像素用例额外检验纯蓝、纯绿、纯红、白、黑的灰度值分别为 29、150、76、255、0，防止仅由同一实现生成期望结果。正常用例检查输出的实际像素和属性；异常用例以明确 ERROR 与非零退出码作为通过条件。

首次自检 T10 为 1920×1080 三通道 uint8 临时测试图，读取至保存耗时为 40.068 ms，满足本机 ≤2 s 的参考目标。该数值仅对应当次数组、编码内容和平台，不是个人图片的性能实测，也不代表其他机器的表现。后续实际自检和正式运行的最新耗时以各批次报告为准。

随后采用用户提供的 `DreamEnding_swing_dusk.jpg`（1192×671、三通道 uint8）和已有黑白图完成正式测试。按用户指示从源图导出彩色 PNG、单通道灰度、透明度测试 PNG、320×180 缩小图及 1920×1080 大图，JPEG 版本逐字节复制原文件。大图等比例放大至 1919×1080 后补齐一列边缘，供尺寸与性能测试；RGBA 保留源图颜色，左侧分别设置 Alpha 为 0 与 128，其余为 255。素材属性及来源见 `input_preparation.md`。

正式测试为 17 项，17 项通过，0 项非预期失败。T10 的 1920×1080 图片处理满足本机 ≤2 s 参考目标，最新具体耗时见 test_report.md。准备过程和正式测试均确认原文件哈希保持不变。

正式结果见 `test_report.md`，实际命令、退出码、属性、哈希、版本和耗时见 `evidence/lab1_latest`。此前的程序自检见 `self_test_report.md`，两类证据分别保留；真实终端截图方法见 `reproduction.md`。

初次环境创建和下载受沙箱写入及网络权限限制，获得授权后成功安装，详细过程见 `installation_notes.md`。WindowsApps 的 Python 占位命令改为 `py` 启动器及虚拟环境绝对路径。中文路径采用字节解码/编码方式支持；灰度图避免访问第三通道；输出限定 PNG 以保留位深。

## 思考题

1. **为什么 imread 返回 None 时不能继续访问 shape？** None 没有数组属性；继续访问会引发 AttributeError，也会掩盖真正的读取失败原因。应先检查读取结果，再处理像素。
2. **为什么同一图片在 OpenCV 和 Matplotlib 中颜色可能不同？** OpenCV 彩色数组按 BGR 排列，Matplotlib 常按 RGB 解释；显示前需交换相应通道，不能直接把 BGR 当 RGB。
3. **float32 或 16 位输入是否仍满足当前需求？** 本实现支持 uint16 并保持位深，输出无损 PNG；float32 明确拒绝。若未来支持浮点输入，须另行约定范围、缩放与输出格式，本次不默默裁剪或转换。
4. **为什么测试必须包含灰度与异常路径？** 灰度的维数不同，能暴露错误的第三通道访问；异常路径验证读取失败是否被及时检查，能发现只在正常图片上运行才被掩盖的问题。
5. **哪些约定应由下一实验继承？** 命令行路径、原图与结果分离、H/W 与 y/x 索引、BGR/BGRA/GRAY、uint8/uint16、Alpha 策略、失败退出码及属性证据结构。本次只记录约定，不实现下一实验。

## 结论与限制

代码、环境、需求和可复现的证据生成链已完成，程序自检与用户素材的正式测试均已通过。以后更换原图，运行 `prepare_inputs.py --source` 导出新素材并更新配置，再执行 `run_tests.py` 即可重新计算结果、哈希和耗时；若直接提供全套符合要求的素材，也可修改配置后直接测试，无需改动源码。

程序按单张静态素材使用，不定义动画、多页图像、浮点 HDR 或色彩管理流程。Alpha 的舍弃结果可能使透明区隐藏像素可见；这是明确的基线约定。性能只对记录的平台与当次输入成立。

图像解码与通道约定参考 [OpenCV 图像读写文档](https://docs.opencv.org/4.x/d4/da8/group__imgcodecs.html)，转换方法参考 [OpenCV 颜色转换文档](https://docs.opencv.org/4.x/de/d25/imgproc_color_conversions.html)。
